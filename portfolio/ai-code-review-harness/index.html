AI 개발 병목은 코드가 아니라 흐름이었다

posted by 손(Son/손민기),
July 05, 2026

왜 필요한지?!

요즘은 AI로 개발하는 게 이상하지 않습니다.

저도 처음에는 코드를 얼마나 빨리 뽑는지가 중요하다고 생각했습니다. 그런데 실제로 써보니 병목은 코드 생성보다 앞뒤에 있었습니다.

  1. 작업 전 플랜 정리
  2. PR 이후 코드리뷰 확인

코드는 빨라졌는데, 방향을 잡는 시간과 리뷰를 기다리는 시간은 변동이 없거나 더 늘어났습니다.

그래서 저는 두 구간을 나눠서 정리했습니다.

병목 정리한 방식
작업 전 플랜 정리 작업 설계 하네스
PR 이후 코드리뷰 Slack 봇 물어보개
반복 확인 10분 단위 watch

이 글에서 말하려는 건 AI 모델 비교가 아닙니다.

AI를 개발 흐름 어디에 붙였고, 사람이 계속 확인하던 일을 어디까지 줄였는지입니다.

작업 전 병목: 플랜 정리

AI에게 대충 시키면 대충 빠릅니다. 무섭게 빠른데, 방향도 같이 틀어집니다.

그래서 작업 전에 브레인스토밍, 아키텍처, 스펙을 먼저 정리하는 구조를 만들었습니다. 매번 AI에게 같은 설명을 반복하지 않기 위해서였습니다.

구조는 아래와 같습니다.

숫자보다 이 구조가 더 중요했습니다. 제가 만든 건 “좋은 프롬프트 하나”가 아니라, 작업을 나누는 방식이었습니다.

영역 역할
system-map 서비스 alias, stack, category, default branch 관리

agents planner, developer, architect, reviewer, verifier 같은 역할 단위
scripts 레포 동기화, 워크스페이스 설정 같은 반복 작업

작업 전에는 선택지와 리스크를 정리하고, 구현 이후에는 PR과 리뷰 대응으로 넘어갑니다.

리뷰 병목: 반복 확인

코드리뷰 요청은 Slack 리뷰 채널에서 시작됐습니다. 개발자가 PR 링크를 올리고, 리뷰어가 확인합니다.

여기에 Slack 리뷰 스레드에서 PR 링크를 받아 코드리뷰를 도와주는 사내 AI 리뷰 봇 물어보개를 붙였습니다.

sequenceDiagram
    actor Dev as 개발자
    participant Slack as Slack 리뷰 채널
    participant Bot as 물어보개
    participant GitHub as GitHub PR
    participant Reviewer as 리뷰어

    Dev->>Slack: PR 링크 공유
    Dev->>Bot: 리뷰 요청
    Bot->>GitHub: 변경사항 확인
    Bot->>GitHub: 리뷰 코멘트 작성
    Dev->>GitHub: 코멘트 반영
    Reviewer->>GitHub: 최종 확인

여기서 중요한 건 첫 리뷰보다 그 이후였습니다.

리뷰 코멘트가 달렸는지, 반영이 끝났는지, approve 가 났는지 계속 확인해야 했습니다. GitHub 를 계속 새로고침하는 일은 개발이 아닙니다. 그냥 집중력을 조금씩 깎아먹는 일에 가깝습니다.

그래서 10분 단위 watch 를 붙였습니다. (1분 단위로 돌면 github api limit 걸려서 10분으로 했습니다.)

sequenceDiagram
    actor Dev as 개발자
    participant Bot as 물어보개
    participant Watch as 10분 watch
    participant GitHub as GitHub PR

    Dev->>Bot: PR 리뷰 요청
    Bot->>GitHub: 리뷰 코멘트 작성
    Dev->>GitHub: 코멘트 반영
    Watch->>GitHub: 신규 코멘트 확인
    alt 추가 코멘트 있음
        Watch-->>Dev: 반영 필요
        Dev->>GitHub: 추가 반영
    else approve 확인
        Watch-->>Dev: watch 해제
        Dev->>GitHub: merge
    end

정리하면 아래와 같습니다.

  1. PR 링크 공유
  2. 물어보개 멘션
  3. 리뷰 코멘트 확인
  4. 코멘트 반영
  5. 10분 단위 watch
  6. approve 확인
  7. approve 되면 watch 해제
  8. 개발자 merge

제가 줄이고 싶었던 건 리뷰 자체보다 반복 확인이었습니다.

실제 흐름은 아래처럼 남습니다.

이 사례에서 좋았던 부분은 리뷰가 한 번으로 끝나지 않았다는 점입니다.

처음에는 코드 자체와 GitHub 체크를 확인했고, merge conflict 때문에 승인하지 않았습니다. 이후 충돌 해소 요청이 올라오자 다시 확인했고, mergeable 상태와 로컬 merge 기준을 재확인한 뒤 승인했습니다.

사람이 계속 보고 있지 않아도, 리뷰가 멈춘 이유와 다음 확인 지점이 스레드에 남습니다.

숫자로 볼 수 있는 것

먼저 물어보개가 실제 리뷰 스레드 안에서 얼마나 쓰였는지 봤습니다.

항목 수치 기준
리뷰 스레드 296개 2025년~2026년, 물어보개가 남긴 리뷰 스레드 기준
PR 링크 388개 리뷰 스레드에서 추출한 GitHub PR 기준
merge 된 PR 362개 created_at → merged_at 계산 가능 PR 기준

같은 스레드에 메시지가 여러 개 있어도 1개로 봤습니다. PR 개수와 완전히 같지는 않지만, 실제 리뷰 흐름 안에서 얼마나 반복적으로 쓰였는지 보기에는 이 기준이 더 낫습니다.

이 숫자는 속도 개선율이 아니라 사용 흔적에 가깝습니다.

한두 번 테스트한 자동화가 아니라, 실제 리뷰 요청 스레드 안에서 반복적으로 사용됐습니다. 그리고 리뷰 요청, 코멘트 확인, 충돌 확인, 재확인, 승인 흐름이 Slack 스레드에 남기 시작했습니다.

제가 보고 싶은 지표도 merge 시간 하나가 아니었습니다.

보고 싶은 것 의미
리뷰 요청 수 실제 업무 흐름 안에서 쓰였는지
코멘트/재확인 기록 리뷰가 한 번으로 끝나지 않고 이어졌는지
approve 전 block 사유 왜 멈췄는지 스레드에 남는지
approve 후 watch 해제 확인 구간이 닫혔는지

제가 줄인 건 merge 버튼까지 걸린 시간이 아니라, 사람이 계속 들여다보는 시간이었습니다.

줄인 시간

PR을 올린 뒤에는 생각보다 자잘한 확인이 많습니다.

리뷰어가 봤는지 기다리고, 코멘트를 반영하고 다시 기다리고, approve 가 났는지 또 확인합니다. 하나씩 보면 별일 아닌데, 계속 반복되면 꽤 피곤합니다.

제가 줄이고 싶었던 시간은 아래에 가깝습니다.

줄인 시간 다시 쓸 곳
리뷰 상태 확인 설계 보완
GitHub 새로고침 테스트 케이스 추가
코멘트 반영 여부 확인 장애 가능성 검토
approve 확인 다음 작업 플랜 정리

개발자가 하루에 집중해서 쓰는 시간은 생각보다 짧습니다.

그래서 반복 확인을 줄이는 건 단순 자동화가 아니라, 좋은 판단을 할 시간을 되찾는 일에 가깝습니다.

앞에서는 작업 방향을 잡고, 뒤에서는 리뷰 상태를 계속 확인합니다.

AI를 붙인 위치도 이 두 지점이었습니다.

정리

중요한 건 AI를 썼다는 사실이 아니라, 어디에 붙였는지였습니다.

구분 정리
작업 설계 브레인스토밍, 아키텍처, 스펙을 작업 설계 하네스로 정리
코드리뷰 Slack 봇 물어보개로 PR 리뷰 요청과 코멘트 확인 연결
Watch 10분 단위로 리뷰 상태 확인
사용 기록 2025년~2026년 Slack 리뷰 스레드 296개, PR 링크 388개, merge PR 362개
효과 merge 시간 단축보다 리뷰 상태 확인, 충돌 확인, 재확인, approve 확인을 흐름 안에 넣은 것

작업 설계 하네스로 AI 개발 전 플랜을 정리하고, Slack 봇 물어보개와 10분 watch 로 PR 리뷰 요청, 코멘트 확인, 반영 확인, approve 확인 흐름을 자동화했습니다.

이력서 문장

작업 설계 하네스와 Slack 봇 물어보개를 활용해 브레인스토밍, 아키텍처 설계, 스펙 작성, PR 리뷰 요청, 10분 단위 리뷰 watch, 셀프 리뷰, 리뷰 검증 흐름을 정리했습니다.
